# DSH 0.2 RC2 full Web profile Loader: two fixed plugins

The prior checks stopped at profile composition and direct ToolRuntime service execution. This check crosses the remaining Loader boundary using official `dsh-v0.2.0-rc.2` at commit `639ed015397290b3745d163aafe02ffee4aa3f84` and the official frozen dependency installation plus `pnpm run build:lib`. A source-only boot is **not** an adequate control: it may register plugin tools while built-in typert contributors fail to import, and the headless profile without a task exits nonzero.

For this narrow replay, a fresh stock `DSH_HOME` boots the real Web profile Loader. Another fresh home installs fixed public GitHub commits `dsh-support-lifecycle-proof@df33364fee39fbb55b53b8c290df6b28d0f072c6` and `dsh-windows-readiness-proof@46cc6b8dbaa0f970ffa326615cb1e52683516929` into the **same** Web profile. The replay asserts that the settled Loader service exists and all four plugin tool names are in the loaded ToolRuntime registry. Web startup uses loopback with port 0, disables browser opening, drops inherited credential-shaped environment variables, suppresses the Web bearer URL from logs, and disposes the profile after inspection. The loader script has a 45-second boot bound.

Local Windows on Node 24.19.0 / pnpm 11.7.0 passed both stock and two-plugin Web profile boots after the official build. The [CI workflow](../../.github/workflows/profile-loader-smoke.yml) repeats the exact pinned tuple on clean Ubuntu and Windows runners. This verifies profile-level tool registration, **not** a model-mediated task, authenticated Web interaction, or the whole 40-Lab catalog. Earlier service-level reports remain separate business-call evidence; neither layer alone should be called complete end-to-end model use.
