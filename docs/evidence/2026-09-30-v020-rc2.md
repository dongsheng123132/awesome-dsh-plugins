# DSH 0.2 RC2: two fixed plugin tuples

On 2026-09-30, the official `dsh-v0.2.0-rc.2` tag resolved to immutable commit `639ed015397290b3745d163aafe02ffee4aa3f84`. A clean Windows worktree passed `pnpm install --frozen-lockfile` with official pnpm 11.7.0, stock CLI help and a fresh `DSH_HOME` headless config composition. Pre-build Windows bin-link warnings did not fail the install.

Two independently isolated DSH_HOME directories installed the public fixed GitHub commits `dsh-support-lifecycle-proof@df33364fee39fbb55b53b8c290df6b28d0f072c6` and `dsh-windows-readiness-proof@46cc6b8dbaa0f970ffa326615cb1e52683516929`. Both appeared in their composed headless configs. Using official Cordis Context, SystemPrompt and ToolRuntime, the first plugin passed inspect, closed-report readback and missing-retirement cases with report SHA-256 `44ad888bce2f282554b8f6afa5971f4c0b1ff9e51bbb6a1918a1122e9f0fb6d6`. The second passed inspect, sanitized 26-control verified-report readback and traversal rejection with SHA-256 `98fd800ccf76f57cea01edbf4e5e21f537a4da368bec6a14f03bca6a44780390`. Replay scripts compare installed bytes with immutable plugin commits and fail if the host source is not the pinned DSH commit.

Both workflows now replay the RC2 tuple on clean Ubuntu and Windows runners, alongside their prior pinned baselines. Linux executes the Windows readiness **evaluator** against a sanitized fixture; it does not become a managed Windows-host observation. These tests prove stock CLI, isolated install/compose and service-level tool calls for two plugins. They do **not** prove full profile Loader startup, model-driven calls, all 40 Labs, or a change to Awesome's default runtime baseline.
