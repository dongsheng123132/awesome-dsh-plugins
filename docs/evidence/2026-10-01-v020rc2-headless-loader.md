# DSH 0.2 RC2 headless Profile Loader proof

This extends the [Web Loader evidence](2026-10-01-v020rc2-profile-loader.md), not a new plugin. The fixed official source is `dsh-v0.2.0-rc.2` at `639ed015397290b3745d163aafe02ffee4aa3f84`. Both plugin sources and `github:` installs are fixed at `dsh-support-lifecycle-proof@df33364fee39fbb55b53b8c290df6b28d0f072c6` and `dsh-windows-readiness-proof@46cc6b8dbaa0f970ffa326615cb1e52683516929`.

The [headless CI workflow](../../.github/workflows/profile-headless-loader-smoke.yml) makes a frozen official install and `build:lib`, then uses **separate fresh** `DSH_HOME` directories for stock and two-plugin headless profiles. The test imports official `runProfile`, observes a real Loader service, checks all four expected names in its ToolRuntime registry, and invokes `dsh_support_lifecycle_inspect` against the fixed plugin repository's sanitized `closed.json` fixture. The business assertion is exactly `componentCount === 2`; it does not copy fixture contents into output. It uses no model credentials, suppresses runtime stdout/stderr, opens no browser, bounds startup and tool execution, and disposes the profile.

The probe supplies a sentinel task solely because the headless command requires one. The run may reject that task after startup because no model agent factory is available. The harness explicitly checks Loader registration and direct ToolRuntime execution before graceful disposal; **it does not claim an agent turn, a final answer, or model-driven tool use**. Likewise, four registered tool names do not certify all Labs or cross-version compatibility. The prior service-level tests remain separate from this full-profile test.

Windows local control: stock headless 24 registered tools; two-plugin headless 28, including all four expected names; direct support inspect returned two components. A separate stock Web regression passed after the probe refactor. See CI for clean Ubuntu/Windows results and the workflow's exact commands.
